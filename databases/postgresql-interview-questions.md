## PostgreSQL Basics

### Q1. What is PostgreSQL?

Open-source object-relational database. Strong standards compliance, extensible, ACID-compliant. Known for advanced features (JSONB, full-text search, GiST/GIN indexes, window functions, CTEs, partitioning, FDWs, custom types).

---

### Q2. What's new in recent Postgres versions?

- **15:** MERGE statement, more parallelism, logical replication improvements
- **16:** parallel hash join, more parallelism, logical replication from standby, faster `pg_dump`
- **17:** improved VACUUM, MERGE supports more operations, JSON_TABLE function

For interview context, mention you keep up with versions and major features.

---

### Q3. PostgreSQL data types — beyond basics?

| Type | Purpose |
|------|---------|
| `SERIAL` / `BIGSERIAL` | Auto-incrementing integer (use `IDENTITY` in modern code) |
| `UUID` | 16-byte unique IDs |
| `JSONB` | Binary JSON, indexable, fast |
| `ARRAY` | Native arrays of any type |
| `HSTORE` | Key-value store column |
| `INET` / `CIDR` | IP addresses |
| `TSVECTOR` / `TSQUERY` | Full-text search |
| `GEOMETRY` (PostGIS) | Spatial data |
| `RANGE` types (`int4range`, `tstzrange`) | Range of values |
| `ENUM` | Enumerated type |
| `INTERVAL` | Time intervals |
| `DOMAIN` | Constrained type |

**Senior point:** Postgres has the richest built-in types of any major OLTP database.

---

### Q4. What's the difference between TIMESTAMP and TIMESTAMPTZ?

- `TIMESTAMP` — no timezone, just date/time
- `TIMESTAMPTZ` — stored as UTC, displayed in session's timezone

**Use TIMESTAMPTZ.** Almost always. Avoids time zone bugs.

```sql
CREATE TABLE events (
  id SERIAL PRIMARY KEY,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

---

### Q5. What is `SERIAL` vs `IDENTITY`?

- `SERIAL` — older syntax, creates a sequence behind the scenes
- `IDENTITY` (SQL standard, Postgres 10+) — cleaner, can be `GENERATED BY DEFAULT` or `GENERATED ALWAYS`

```sql
-- Old
id SERIAL PRIMARY KEY,

-- New (preferred)
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
```

## MVCC and Vacuum

### Q6. What is MVCC in Postgres?

Multi-Version Concurrency Control. Each row has hidden columns (`xmin`, `xmax`) tracking which transactions can see it. When you UPDATE, the old row stays (with `xmax` set), and a new row is inserted.

**Effects:**
- Readers don't block writers, writers don't block readers
- Each transaction sees a consistent snapshot
- Old row versions accumulate ("dead tuples")
- VACUUM reclaims space from dead tuples

---

### Q7. What is VACUUM?

Reclaims space from dead row versions and updates statistics.

```sql
VACUUM;          -- light, marks space reusable
VACUUM ANALYZE;  -- + update stats for planner
VACUUM FULL;     -- rewrites table, locks it (expensive)
```

Postgres has **autovacuum** running in background. Tune it to fit your workload.

---

### Q8. What is bloat in Postgres?

Wasted space from old row versions or empty pages. Causes:
- Heavy UPDATE workloads
- Long-running transactions blocking VACUUM
- Disabled autovacuum
- Slow autovacuum

**Symptoms:** table size grows much faster than data; queries slow down.

**Fix:** `VACUUM FULL` (locks), `pg_repack` (online), or `CLUSTER` (rewrites by index order).

---

### Q9. What is transaction wraparound?

Postgres uses 32-bit transaction IDs. After ~2 billion transactions, IDs wrap around. Postgres prevents this by freezing old rows. If autovacuum can't keep up, the DB will refuse connections to prevent data loss.

**You should never see this if autovacuum is healthy.** Monitor `age(datfrozenxid)` per database.

---

### Q10. Long-running transactions and VACUUM?

A long-running transaction holds an old snapshot, preventing VACUUM from cleaning rows newer than its snapshot. Bloat accumulates.

**Avoid:** transactions that run for minutes/hours. Use connection pool timeouts. Monitor `pg_stat_activity` for old `xact_start`.

## Indexes — Postgres Specifics

### Q11. Index types in Postgres?

| Type | Use case |
|------|----------|
| B-tree (default) | Equality, range, sort |
| Hash | Equality only (rarely faster than B-tree) |
| GIN | Full-text, JSONB, arrays |
| GiST | Geometric, full-text, range |
| SP-GiST | Specialized partition (e.g., quad-trees) |
| BRIN | Huge tables with naturally ordered data (block-range index) |
| Bloom | Multi-column filtered (specialized extension) |

---

### Q12. When to use GIN vs GiST?

- **GIN:** faster reads, slower writes, larger size. For static data, full-text, JSONB.
- **GiST:** balanced, smaller, slower reads. For dynamic data, geometry.

For JSONB and full-text: **GIN is the default choice.**

---

### Q13. What is BRIN and when to use it?

Block Range Index. Stores summary (min/max) per block of pages. Tiny in size.

Best for huge tables where data is **physically ordered** (e.g., time-series with `created_at` always inserted in order).

```sql
CREATE INDEX ON events USING BRIN (created_at);
```

For a 100M-row table, BRIN can be a few KB vs GB for B-tree, with similar query performance for range queries.

---

### Q14. What is a partial index?

Index over a subset of rows.

```sql
-- Index only active users
CREATE INDEX idx_active_users ON users (email) WHERE active = true;
```

Smaller, faster. Useful when most queries filter on a common condition.

---

### Q15. What is an expression index (functional index)?

Index over an expression's result.

```sql
-- Search by lowercase email
CREATE INDEX idx_users_email_lower ON users (LOWER(email));

-- Now this query uses the index
SELECT * FROM users WHERE LOWER(email) = LOWER('Alice@Example.com');
```

---

### Q16. What is `CREATE INDEX CONCURRENTLY`?

Builds an index without locking the table for writes. Slower (multiple table scans), but safe in production.

```sql
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id);
```

**Always use CONCURRENTLY in production.** A regular CREATE INDEX locks the table.

---

### Q17. How do you find unused indexes?

```sql
SELECT 
  schemaname, relname, indexrelname,
  idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

Indexes with 0 scans are candidates for removal (unless they enforce uniqueness).

## JSON and JSONB

### Q18. JSON vs JSONB?

| JSON | JSONB |
|------|-------|
| Stored as text | Stored as binary |
| Preserves whitespace, key order, duplicates | Normalized |
| Slower processing | Faster processing |
| No indexing on contents | GIN-indexable |
| Smaller for short docs | Larger but faster |

**Use JSONB.** Always. JSON is essentially never the right choice unless you need to preserve the exact original text.

---

### Q19. JSONB query operators?

```sql
-- Get key
SELECT data->'name' FROM users;          -- returns JSONB
SELECT data->>'name' FROM users;         -- returns text

-- Path
SELECT data#>'{address,city}' FROM users;
SELECT data#>>'{address,city}' FROM users;

-- Contains (uses GIN index)
SELECT * FROM products WHERE attrs @> '{"color": "red"}';

-- Exists key
SELECT * FROM products WHERE attrs ? 'discount';
```

---

### Q20. How do you index JSONB?

```sql
-- General GIN index — supports @>, ?, ?|, ?&
CREATE INDEX idx_products_attrs ON products USING GIN (attrs);

-- Index a specific path (smaller, faster)
CREATE INDEX idx_products_color ON products ((attrs->>'color'));
```

---

### Q21. When NOT to use JSONB?

- Data has consistent structure (use proper columns)
- Need foreign keys
- Need strong typing
- Frequent partial updates of one nested field (must rewrite whole JSONB)

**Senior rule:** JSONB is great for variable schemas (user prefs, product attributes, audit logs). It is terrible as a substitute for proper relational design.

## Transactions and Isolation

### Q22. Default isolation level in Postgres?

**READ COMMITTED.** Each statement sees a snapshot of committed data at statement start.

For stricter behavior:
```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

---

### Q23. Postgres SERIALIZABLE — what's special?

Postgres uses **Serializable Snapshot Isolation (SSI)**. Detects serialization conflicts and aborts transactions that would violate serializability.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
  -- ...
COMMIT;
-- May get: ERROR: could not serialize access due to concurrent update
```

App must retry on serialization failures (`40001`).

---

### Q24. `SELECT FOR UPDATE` in Postgres?

```sql
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
```

Locks the row; others wait. Use for read-then-modify patterns.

Variants:
- `FOR NO KEY UPDATE` — weaker lock, allows foreign-key-only changes elsewhere
- `FOR SHARE` — shared lock, others can read but not write
- `FOR KEY SHARE` — for foreign key checks

---

### Q25. What is advisory lock?

Application-level lock on an arbitrary key. Postgres doesn't enforce a meaning; you choose.

```sql
SELECT pg_advisory_lock(12345);  -- session lock, manual unlock
SELECT pg_advisory_xact_lock(12345);  -- transaction lock, auto-released

-- Try without blocking
SELECT pg_try_advisory_lock(12345);
```

Use cases: cron jobs that should only run once cluster-wide; batch processing one user at a time.

---

### Q26. How do you handle deadlocks in Postgres?

Postgres detects and aborts one transaction with `40P01`. App retries.

**Prevent:** acquire locks in deterministic order (e.g., always update by ID ASC).

## Query Optimization in Postgres

### Q27. EXPLAIN vs EXPLAIN ANALYZE?

- `EXPLAIN` — shows plan without executing
- `EXPLAIN ANALYZE` — actually executes, shows real timings
- `EXPLAIN (ANALYZE, BUFFERS)` — also shows buffer cache hits

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 123;
```

Output:
```
Index Scan using idx_orders_user_id on orders  (cost=0.43..8.45 rows=1 width=24) (actual time=0.045..0.046 rows=1 loops=1)
  Index Cond: (user_id = 123)
Planning Time: 0.150 ms
Execution Time: 0.073 ms
```

---

### Q28. Reading the plan — what to look for?

- **Seq Scan** — full table scan. Bad on big tables with selective filters.
- **Index Scan** — using an index, fetches rows. Usually good.
- **Index Only Scan** — best, no row lookup.
- **Bitmap Heap Scan + Bitmap Index Scan** — multiple matching rows, batched lookup.
- **Nested Loop** — for small inner side.
- **Hash Join** — for big sets, builds hash table.
- **Merge Join** — for sorted inputs.

If `actual rows` differs hugely from `cost rows estimate` → stats are stale. Run `ANALYZE`.

---

### Q29. What is the `pg_stat_statements` extension?

Tracks query execution statistics. Most important Postgres tool.

```sql
CREATE EXTENSION pg_stat_statements;

-- Top queries by total time
SELECT query, calls, total_exec_time, mean_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

Identifies queries that are slow OR frequent (often more important).

---

### Q30. Tune `work_mem`?

Memory per query operation (sort, hash). Default is small (4MB). For large queries with sort/hash, increase.

```sql
SET work_mem = '256MB';  -- session-level
```

Don't set globally too high — every connection × every operation × work_mem can exhaust memory.

---

### Q31. Tune `shared_buffers`?

Postgres memory for caching pages. Recommend 25% of RAM (Postgres relies on OS cache too, unlike MySQL InnoDB which is more aggressive).

```ini
shared_buffers = 4GB    -- on a 16GB machine
```

---

### Q32. What's `effective_cache_size`?

Estimate of how much memory the planner can assume is available for caching (Postgres + OS cache combined). Doesn't allocate; helps planner pick good plans.

Recommend ~50-70% of RAM.

## Replication and HA

### Q33. Postgres replication types?

| Type | Description |
|------|-------------|
| Streaming (physical) | WAL stream from primary to replicas. Replica is exact byte-copy. |
| Logical | Stream specific tables/databases. Schema can differ. |
| Cascading | Replica replicates from another replica. |
| Synchronous | Primary waits for replica acknowledgment before commit. |
| Asynchronous | Default, lower latency. |

---

### Q34. Streaming replication setup?

On primary:
```ini
wal_level = replica
max_wal_senders = 10
```

On replica:
```ini
primary_conninfo = 'host=primary user=replication'
```

Use `pg_basebackup` to create the initial replica. Tools like Patroni for automatic failover.

---

### Q35. What is logical replication?

Stream specific tables. Replica can have different version, structure (compatible).

```sql
-- On primary
CREATE PUBLICATION my_pub FOR TABLE users, orders;

-- On replica
CREATE SUBSCRIPTION my_sub 
CONNECTION 'host=primary dbname=mydb user=replicator'
PUBLICATION my_pub;
```

Use cases: zero-downtime upgrades, ETL into a different schema, multi-region replication of subset.

---

### Q36. How do you fail over to a replica?

1. Promote replica: `pg_ctl promote` or `SELECT pg_promote();`
2. Repoint app traffic to new primary
3. Old primary needs to be re-synced to follow new primary (or rebuilt)

**Patroni / Stolon / repmgr** automate this. Cloud-managed (RDS, Aurora) handles it for you.

---

### Q37. Replication lag — how to measure?

```sql
-- On replica
SELECT now() - pg_last_xact_replay_timestamp() AS replication_lag;

-- Or in seconds  
SELECT EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp()));
```

Alert if lag > N seconds.

## Advanced Features

### Q38. What is partitioning?

Splitting a large table into smaller "partitions." Two main strategies:

- **Range partitioning:** by date or numeric range (`created_at`)
- **List partitioning:** by discrete values (`country`)
- **Hash partitioning:** by hash (even distribution)

```sql
CREATE TABLE events (
  id BIGSERIAL,
  created_at TIMESTAMPTZ NOT NULL,
  data JSONB
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2025_01 PARTITION OF events
  FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
```

Benefits:
- Queries filtered on partition key only scan relevant partitions
- DROP PARTITION is instant cleanup (vs DELETE)
- Smaller indexes per partition

---

### Q39. What is a materialized view?

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT DATE(created_at) AS day, SUM(amount) AS revenue
FROM orders GROUP BY DATE(created_at);

REFRESH MATERIALIZED VIEW daily_revenue;
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;  -- doesn't lock reads
```

Use for: expensive aggregates that don't need to be real-time.

---

### Q40. What is a foreign data wrapper (FDW)?

Connect to external data sources as if they were tables.

```sql
CREATE EXTENSION postgres_fdw;
CREATE SERVER remote_db FOREIGN DATA WRAPPER postgres_fdw 
  OPTIONS (host 'other-host', dbname 'mydb');
CREATE FOREIGN TABLE remote_users (...) SERVER remote_db OPTIONS (table_name 'users');

SELECT * FROM remote_users WHERE id = 123;  -- queries the remote DB
```

Other FDWs: file_fdw, mongodb_fdw, mysql_fdw.

---

### Q41. What is Row Level Security (RLS)?

Filter rows automatically based on the current user.

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY orders_user_isolation ON orders
  FOR ALL TO app_user
  USING (user_id = current_setting('app.current_user_id')::INT);
```

Now `SELECT * FROM orders` returns only the current user's orders. Powerful for multi-tenant apps.

---

### Q42. What is `LISTEN/NOTIFY`?

Postgres-native pub/sub.

```sql
-- Listener
LISTEN order_created;

-- Sender
NOTIFY order_created, '{"id": 123}';
```

App receives the notification asynchronously. Useful for cache invalidation, simple queues. Not durable — for that, use a real queue (RabbitMQ, Kafka).

---

### Q43. What are CTEs in Postgres?

Same as standard SQL. **Materialization changed in 12+:** before 12, CTEs were always materialized (could be slow). Now optimizer can inline non-recursive CTEs by default.

```sql
WITH active AS NOT MATERIALIZED (...)  -- inline
WITH active AS MATERIALIZED (...)      -- force materialization
```

---

### Q44. What is `INSERT ... ON CONFLICT` (UPSERT)?

```sql
INSERT INTO users (email, name) VALUES ('a@a.com', 'Alice')
ON CONFLICT (email) DO UPDATE SET name = EXCLUDED.name;

-- Or do nothing on conflict
ON CONFLICT (email) DO NOTHING;
```

`EXCLUDED` references the row that would have been inserted.

Idempotent inserts → critical for ingestion pipelines.

---

### Q45. What are `RETURNING` clauses?

Return data from a modifying statement.

```sql
INSERT INTO users (email) VALUES ('a@a.com') RETURNING id, created_at;
UPDATE orders SET status = 'shipped' WHERE id = 5 RETURNING *;
DELETE FROM logs WHERE created_at < '2024-01-01' RETURNING id;
```

Single round trip for insert + select.

## Operational Concerns

### Q46. How do you back up Postgres?

| Tool | Type |
|------|------|
| `pg_dump` | Logical, single DB |
| `pg_dumpall` | Logical, all DBs + roles |
| `pg_basebackup` | Physical, base for replication |
| Continuous archiving (WAL) + `pg_basebackup` | PITR |
| Cloud snapshots | Physical, fast |

For PITR: `pg_basebackup` + WAL archiving (e.g., to S3 via WAL-G or pgBackRest).

---

### Q47. How do you monitor Postgres?

Key metrics:
- Active connections / max
- Long-running queries
- Replication lag
- Cache hit ratio (`pg_stat_database`)
- Bloat (table & index)
- Autovacuum activity
- Disk usage / WAL accumulation
- pg_stat_statements top queries
- Lock waits (`pg_locks`, `pg_stat_activity`)

Tools: Datadog, pganalyze, pgwatch2, AWS RDS Performance Insights.

---

### Q48. What is `pg_stat_activity`?

Snapshot of current sessions and queries.

```sql
-- Long-running queries
SELECT pid, query, state, age(now(), query_start) AS runtime
FROM pg_stat_activity
WHERE state = 'active' AND query_start < now() - interval '1 minute'
ORDER BY runtime DESC;

-- Idle transactions (blocking VACUUM)
SELECT pid, query, age(now(), xact_start) AS xact_age
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_age DESC;
```

---

### Q49. How do you kill a query?

```sql
-- Cancel
SELECT pg_cancel_backend(pid);

-- Force terminate (closes connection)
SELECT pg_terminate_backend(pid);
```

---

### Q50. Connection pooling?

Postgres has high per-connection overhead. With many concurrent connections (>100), use a pooler:

- **PgBouncer** — lightweight, transaction-pooling mode is most efficient
- **Pgpool** — more features but more complex
- **Built-in pool in app** (pg-pool, pgx) — fine for small scale

---

### Q51. What is an extension? Common ones?

Postgres extensions add features.

```sql
CREATE EXTENSION pg_stat_statements;
CREATE EXTENSION uuid-ossp;
CREATE EXTENSION postgis;
CREATE EXTENSION pg_trgm;          -- trigram, fuzzy text matching
CREATE EXTENSION pgcrypto;
CREATE EXTENSION btree_gin;
CREATE EXTENSION timescaledb;       -- time-series
```

Common in production:
- `pg_stat_statements` (must-have)
- `pg_trgm` (LIKE search)
- `uuid-ossp` (UUID generation)
- `postgis` (geo)
- `timescaledb` (time-series)

## Real Interview Scenarios

### Scenario 1: "Schema migration locked our table for 30 min."

**Diagnosis:** likely `ALTER TABLE ADD COLUMN NOT NULL DEFAULT ...` rewrites the table.

**Fix:** split into safe migrations:
```sql
-- Step 1: add nullable column
ALTER TABLE big_table ADD COLUMN new_col TEXT;

-- Step 2: backfill in batches
UPDATE big_table SET new_col = ... WHERE id BETWEEN 1 AND 10000;
-- repeat in chunks

-- Step 3: enforce NOT NULL
ALTER TABLE big_table ALTER COLUMN new_col SET NOT NULL;
```

---

### Scenario 2: "Slow query started this week, no code change."

**Diagnosis:**
1. `EXPLAIN ANALYZE` — what's the plan now?
2. Compare to expected plan
3. Check stats: `SELECT * FROM pg_stats WHERE tablename = '...' AND attname = '...';`
4. If estimates are wildly off → `ANALYZE table_name`
5. If stats updated, plan still bad → check if data distribution changed (skew)

---

### Scenario 3: "Disk is full because of WAL."

**Cause:** replication slot pointing to a replica that's down or far behind. Postgres keeps WAL until consumed.

**Diagnosis:**
```sql
SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;
```

**Fix:** drop the inactive slot OR repair the replica.

```sql
SELECT pg_drop_replication_slot('slot_name');
```

---

### Scenario 4: "Random rows take 5 seconds; mostly fast."

**Likely:** some rows have very large TOAST (out-of-line storage for large values). Loading those triggers extra I/O.

**Fix:**
- Check column types — a JSONB column with huge documents
- Move large data to separate table
- Or to object storage with reference

---

### Scenario 5: "We need to do a complex search."

**Decision tree:**
- Simple LIKE: B-tree won't help with leading wildcard. Use `pg_trgm` GIN index.
- Full-text natural language: `tsvector` + GIN
- Multi-attribute filter + text: combine
- Massive scale: external search (Elasticsearch / OpenSearch)

```sql
-- Trigram index for LIKE '%foo%'
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_search ON products USING gin (name gin_trgm_ops);

-- Full-text search
CREATE INDEX idx_doc ON articles USING gin (to_tsvector('english', body));
SELECT * FROM articles WHERE to_tsvector('english', body) @@ plainto_tsquery('english', 'machine learning');
```

## Senior Postgres Mantra

1. **JSONB > JSON. Always.**
2. **TIMESTAMPTZ > TIMESTAMP. Always.**
3. **CREATE INDEX CONCURRENTLY in production.**
4. **EXPLAIN ANALYZE + pg_stat_statements.**
5. **Watch for bloat and idle-in-transaction.**
6. **Read replicas for read scaling.**
7. **Use partitioning for huge time-series tables.**
8. **Test PITR quarterly.**
